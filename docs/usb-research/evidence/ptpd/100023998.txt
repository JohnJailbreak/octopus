===== PTPResponder handleData: and handleStartData: =====
Decoded from the device's own /usr/libexec/ptpd, SHA-256
a1742358da3e257204a0f190211cda26a155dfe0dabb3c9fa572117460085dcb, 417184 bytes, with a reader
written for this purpose: no disassembler here reads Mach-O arm64e. Call targets named from
functions.tsv; "xzr" in a load or store is the stack pointer, which register 31 means there.

What it establishes, which decides how uploads can be received:

- handleStartData: is a single ret. Nothing is given to it, so the total length does not arrive
  that way, and there is nothing to hook for the start of a transfer.
- handleData: takes ONE packet holding the WHOLE data phase. It calls [packet data] once and hands
  that object straight on. There is no loop, no offset, no accumulation, no second call. So the
  transport assembles every chunk before calling it, and a handler of ours receives a complete file
  in one call. That was the open question before writing one.
- It dispatches on [packet operationCode] and knows exactly two: 0x900E, which passes the data to
  assignHostSupportedFormats:, and 0x900B, to assignHostMediaCapabilities:. Both are Apple's own
  vendor operations, and both are the pattern an upload must follow.
- Anything else answers 0x2019 DeviceBusy and clears a flag at ivar 0x8c. So returning YES from
  handleRequest: without also handling handleData: would make Apple answer DeviceBusy, not hang.
- The responder holds its transport at ivar 0x8 and the current transaction ID at ivar 0x38.
- A response is [[PTPOperationResponsePacket alloc] initWithResponseCode:transactionID:] or the
  parameter1: form, then [transport sendResponse:]. That is the whole of how ptpd answers a host.
